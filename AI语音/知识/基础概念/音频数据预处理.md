# 音频数据预处理

## 1. 身份

音频数据预处理是把原始录音变成模型可训练、可评估、可部署输入的工程链路。它不是固定流水线，而是围绕任务选择：先统一格式和质量，再切分、清理、标注，最后转成 waveform、[[方向/AI语音/知识/基础概念/Spectrogram（声谱图）|spectrogram]]、SSL 特征、codec token 或 latent。

## 2. 常见流程

```text
原始音频
  -> 格式检查
  -> 重采样 / 转单声道 / 统一位深
  -> 音量归一化
  -> 静音裁剪 / VAD
  -> 降噪 / 去混响 / 去爆音
  -> 切分 / 对齐 / 标注
  -> 特征提取或 tokenizer / codec 编码
  -> 训练样本
```

## 3. 格式统一

| 处理 | 作用 |
|---|---|
| 转 WAV / FLAC | 避免 MP3/AAC 等有损压缩带来的不稳定 |
| 重采样 | 统一采样率，如 16 kHz、24 kHz、48 kHz |
| 单声道 / 多声道处理 | ASR 常转 mono；阵列、空间音频和 [[方向/AI语音/知识/基础概念/DOA（到达方向）]] / 声源定位任务保留多通道 |
| 统一位深 | 常见 [[方向/AI语音/知识/基础概念/PCM16（16-bit Pulse Code Modulation）]] / float32 |
| 去坏文件 | 检查空音频、截断、损坏、采样率错误 |

## 4. 音量与动态范围

| 处理 | 作用 |
|---|---|
| Peak normalization | 按 [[方向/AI语音/知识/基础概念/Level（电平）]] 控制峰值，防止峰值过大或过小 |
| RMS / LUFS normalization | 统一主观响度 |
| clipping 检测 | 找出过载削波音频 |
| DC offset removal | 去掉波形整体偏移 |
| dynamic range check | 排除过度压缩或极弱音频 |

## 5. 切分与静音处理

| 处理 | 作用 |
|---|---|
| [[方向/AI语音/知识/基础概念/VAD（Voice Activity Detection）]] | 找出有人声的片段 |
| 静音裁剪 | 去掉头尾或长段静音 |
| 固定窗口切块 | 长音频切成 5s、10s、30s 等 |
| overlap chunking | 保留上下文，减少边界伪影 |
| endpointing | 判断一句话开始/结束 |

ASR 常见链路：

```text
长录音 -> VAD -> 语音段 -> ASR
```

语音增强 / Flow Matching 常见链路：

```text
长音频 -> overlapping chunks -> 每块增强 -> overlap-add 拼回
```

## 6. 清理与质量控制

| 处理 | 作用 |
|---|---|
| 降噪 | 去背景噪声 |
| 去混响 | 减少房间反射 |
| 去爆音 / pop removal | 处理喷麦、点击、脉冲噪声 |
| 去电流声 / hum removal | 处理 50/60 Hz 嗡声 |
| SNR 估计 | 过滤过脏样本 |
| 语音/非语音分类 | 删除音乐、纯噪声、无关片段 |
| 重复检测 | 去掉重复录音或重复句子 |

## 7. 标注与对齐

| 处理 | 作用 |
|---|---|
| 文本清洗 | 统一大小写、标点、数字、特殊符号 |
| transcript 对齐 | 音频和文本匹配 |
| forced alignment | 获取词级/字级时间戳 |
| speaker labeling | 标注说话人 |
| diarization | 多人录音切分说话人 |
| 语言识别 | 多语言数据分桶 |
| 情绪/风格标签 | TTS 或语音理解任务使用 |

## 8. 特征提取

| 表示 | 常见用途 |
|---|---|
| waveform | 端到端模型、语音增强 |
| STFT / [[方向/AI语音/知识/基础概念/Spectrogram（声谱图）]] | 传统增强、频域模型 |
| [[方向/AI语音/知识/基础概念/Spectrogram（声谱图）]] / mel spectrogram | ASR、TTS、音频分类 |
| [[方向/AI语音/知识/基础概念/Fbank（滤波器组特征）]] | ASR encoder、语音 tokenizer、Whisper-like 前端 |
| MFCC | 传统语音识别、轻量模型 |
| [[方向/AI语音/知识/基础概念/SSL 编码器]] 特征 | [[方向/AI语音/模型/WavLM]]、[[方向/AI语音/模型/HuBERT]]、wav2vec 表示 |
| [[方向/AI语音/知识/基础概念/NAC（神经音频 Codec）]] / codec token | TTS、codec LM、语音生成 |
| VAE / latent | diffusion / [[方向/AI语音/知识/基础概念/Flow Matching（流匹配）]] / DiT |

## 9. 数据增强

| 增强 | 作用 |
|---|---|
| [[方向/AI语音/知识/基础概念/Mix（语音混合）]] / 加噪 | 提升噪声鲁棒性，构造 noisy-clean 或多人重叠样本 |
| RIR 卷积 | 模拟混响 / 远场 |
| speed perturbation | 改语速 |
| pitch shift | 改音高 |
| gain perturbation | 改响度 |
| codec simulation | 模拟 Opus/MP3/电话压缩 |
| packet loss | 模拟 VoIP 丢包 |
| bandwidth limitation | 模拟电话 8 kHz |
| mixup / overlap speech | 模拟多人重叠说话 |
| [[方向/AI语音/知识/基础概念/Underwater-like Filtering（水下感滤波）]] | 复合退化：低通 + 混响 + 介质调制 + 链路带限，模拟水下语音传输 |

### 9.1. 语音增强训练的扩增维度

语音增强的训练样本通常从干净语音 $s(t)$ 构造退化输入 $y(t)$：

$$
y(t) = \alpha \cdot (h * s)(t) + \beta \cdot n(t) + \gamma \cdot i(t)
$$

其中 $h$ 是房间脉冲响应，$n(t)$ 是背景噪声，$i(t)$ 是干扰说话人或其他声源；$\alpha$、$\beta$、$\gamma$ 由随机电平、SNR 和 SIR 控制。常见扩增维度如下：

| 扩增维度 | 常见做法 | 主要覆盖的真实变化 |
|---|---|---|
| 噪声混合 | 随机叠加稳态、非稳态、人群、音乐、设备噪声 | 不同噪声类型与 SNR |
| 混响模拟 | 随机 RIR 卷积，改变房间、距离、RT60、DRR | 远场与不同房间声学 |
| 干扰语音 | 加入另一说话人、电视对白或多人重叠语音 | 串音、会议和语音重叠 |
| 电平扰动 | 随机 gain、响度、动态范围、轻微削波 | 不同录音距离与设备增益 |
| 设备与信道 | 频响、带宽、重采样、codec、丢包、突发静音 | 手机、耳机、电话和 VoIP 链路 |
| 空间条件 | DOA、通道延迟、增益/相位、麦克风缺失 | 阵列麦克风与多通道部署 |
| 时频扰动 | 时间遮挡、频率遮挡、局部频带衰减 | 特征级正则化与缺失频带 |

### 9.2. 推荐的数据构造顺序

对大多数单通道语音增强任务，可以先采用下面的基础配方：

```text
干净语音
  -> 随机增益
  -> 随机 RIR 混响
  -> 按随机 SNR 叠加背景噪声
  -> 可选：加入干扰说话人
  -> 可选：模拟设备频响、codec 或带宽限制
  -> noisy input + clean target
```

如果目标是会议、远场或多人场景，再提高非平稳噪声、干扰语音、时变 SNR 和空间扰动的比例。DNS Challenge 的数据和任务设置可作为通信降噪场景的参考入口，[[方向/AI语音/模型/NSNet2]] 则记录了 SNR、谱形状和 level augmentation 对实时降噪训练的具体经验。

### 9.3. 训练时的注意事项

- **优先做物理合理的复合退化**：噪声、RIR、设备响应和带宽限制通常比孤立的单一扰动更接近真实部署。
- **保持输入与目标对齐**：监督式增强中，应用于 clean target 的变换必须与 degraded input 的物理过程一致；不要对输入独立做强时频遮挡后仍把原始 clean 直接当作严格标签。
- **SNR/SIR 不要只取少数固定值**：应在目标场景范围内连续或分段随机采样，避免模型记住少数条件。
- **合成数据与真实数据混合**：合成数据负责覆盖条件，真实录音负责约束设备、房间和噪声分布；验证集应尽量保留真实场景。
- **扩增强度要受部署分布约束**：过强的 pitch、speed、codec 或频谱扰动会制造训练集特有伪影，反而损害语音保真度。
- **特征级扩增要谨慎**：SpecAugment 可以作为 STFT 或 log-mel 模型的正则化手段，但它原本主要服务于 ASR，语音增强中应单独验证对内容保持和波形重建的影响。

### 9.4. 一句话经验

**先覆盖真实退化分布，再增加扰动种类；先保证 noisy-clean 配对正确，再追求扩增数量。**

## 10. 按任务取舍

| 任务 | 重点预处理 |
|---|---|
| ASR | 重采样、VAD、切分、文本清洗、对齐、噪声/方言增强 |
| TTS | 高质量录音筛选、响度统一、文本规范化、说话人/风格标签 |
| 语音增强 | 构造 noisy-clean paired data、RIR、噪声、codec、SNR 控制 |
| 说话人识别 | VAD、去静音、说话人分段、避免泄漏同一说话人 |
| 音频分类 | 重采样、片段切分、[[方向/AI语音/知识/基础概念/Spectrogram（声谱图）]] / mel / STFT、类别均衡 |
| 语音 Agent | VAD、端点检测、低延迟切块、回声消除、降噪 |

## 11. 按模型取舍

这张表只记录工程前处理口径，不记录模型排行榜。原则：优先按模型/服务官方 processor、SDK 或 API 接口来喂音频；只有离线批处理、长音频和实时链路才额外设计 chunk。

| 模型/路线 | 是否需要 chunk / 分段 | 采样率 / 音频口径 | 工程提醒 |
|---|---|---|---|
| [[方向/AI语音/模型/Whisper]] | 是。模型核心输入是 30s 窗口；长音频要切窗、滑窗或先 VAD 再拼接文本。 | 16 kHz mono log-Mel。 | 30s 是模型窗口，不等于语义句段；字幕/会议场景还要做时间戳合并和重复去除。 |
| [[方向/AI语音/模型/Qwen3-ASR]] | 本地 HF processor 默认 `chunk_length=30`；云端长音频工具链可用 VAD 分段，默认目标 120s；实时版走连续流 + server VAD。 | 本地特征提取默认 16 kHz、128-bin log-Mel；QwenCloud realtime 示例用 `sample_rate=16000`。 | 本地、文件转写、实时三种入口不要混口径；要时间戳时还要考虑 ForcedAligner 的分段约束。 |
| [[方向/AI语音/模型/FunASR]] | 是。非流式长音频通常先 FSMN-VAD 切短段；流式 Paraformer 用 chunk + cache，常见 `[0,10,5]` 表示 600ms 输出粒度 + 300ms lookahead。 | 工程示例通常按 16 kHz ASR 口径；具体模型以 ModelScope/FunASR 配置为准。 | FunASR 更像工具链：ASR、VAD、标点、说话人、热词要按任务组合，不要只看主 ASR 模型。 |
| [[方向/AI语音/模型/GPT-4o Transcribe]] / `gpt-transcribe` | API 可不传 chunk，默认单块；`chunking_strategy=auto/server_vad` 时服务端按 VAD 切；diarize 长于 30s 时需要 chunking。 | 文件 API 接收 wav/mp3/flac/m4a/ogg/webm 等容器；公开接口层不要求用户固定重采样。 | 如果要稳定字幕或会议段落，建议显式记录 chunking 策略，否则同一音频的段落边界难复现。 |
| [[方向/AI语音/模型/OpenAI Realtime]] | 连续流。分段主要由 server VAD / turn detection 决定，不是离线固定窗。 | PCM 模式为 24 kHz、16-bit、mono；也支持 G.711 u-law / a-law。 | Realtime 的 transcript 是异步辅助文本；模型本身直接消费音频，不能把 transcript 当作唯一输入表示。 |
| [[方向/AI语音/模型/Seed-ASR]] | 待核。公开技术报告强调 AcLLM 连续语音表示 + 上下文，但未给稳定工程 chunk 参数。 | 待核。不要默认照搬 Whisper 的 16 kHz / 30s。 | 当前更适合作论文对标；落地前先找官方 API/SDK 或复现实作的 processor。 |
| [[方向/AI语音/模型/Voxtral]] | 离线版本主要靠长上下文承载长音频；Realtime 版本是原生流式，具体 chunk delay 由实现/API 控制。 | Transformers / serving 口径常见 16 kHz 音频处理；Voxtral TTS 分支另是 24 kHz 输出路线。 | 同名 Voxtral 已有 ASR/理解、Realtime、TTS 分支，记录时必须区分分支。 |
| [[方向/AI语音/模型/Qwen3-Omni]] / [[Qwen2.5-Omni]] | 交互式场景走流式；离线音频/视频理解由 qwen-omni-utils / processor 处理。 | 本地 cookbooks 常把音频解码到 16 kHz 展示；实际入口按 processor / API 读取。 | Omni 适合音频理解和语音交互；纯 ASR 批处理仍优先专用 ASR，便于复查和对齐。 |
| [[方向/AI语音/模型/Qwen3-TTS]] | 生成端是流式 token / audio chunk；voice cloning 通常只需约 3s 参考音频，不需要把参考音频切长段。 | 开源 tokenizer 输出 24 kHz 口径；Qwen TTS realtime 默认 24 kHz，部分非实时 API 可选 8/16/24/48 kHz。 | `12Hz` 是语音 token 帧率，不是音频采样率；参考音频可传文件、URL、base64 或 `(array, sample_rate)`。 |
| [[方向/AI语音/模型/Spark-TTS]] | TTS 文本按句/段落切更稳；参考音频不宜无限加长，按 voice cloning 条件使用。 | BiCodec 配置口径为 16 kHz。 | 重点是文本规范化、参考音频干净度和说话人属性；chunk 更多是长文本合成策略。 |
| [[方向/AI语音/模型/ZONOS2]] | 推理以文本段落/服务端生成块为主；MLX 转换当前提示 streaming 未实现。 | 输出 mono 44.1 kHz；参考音频由 speaker encoder 提取 embedding。 | 高保真 TTS 不要为了省事强行降到 16 kHz；除非下游电话/ASR 口径要求。 |
| [[方向/AI语音/模型/Moshi]] | 是原生流式对话模型；Mimi codec 以 80ms 帧延迟流式编码。 | Mimi 处理 24 kHz 音频，压到 12.5 Hz 表示。 | 适合低延迟双工对话；不要把它当离线 ASR 固定 30s chunk 模型。 |
| [[方向/AI语音/模型/X-Codec2]] | codec/tokenizer 本身按连续语音编码；实时 TTS 是否 chunked 解码要实测。 | 16 kHz speech codec，约 50 tokens/s。 | 50 tokens/s 只说明 token 帧率；真实实时性取决于 decoder RTF 和边界伪影。 |
| [[方向/AI语音/模型/WavLM]] / [[方向/AI语音/模型/HuBERT]] | 双向 SSL encoder 不原生流式；如要上线，多用重叠 chunk + 只保留中间帧，或换 streaming encoder。 | 通常按 16 kHz speech encoder 口径。 | chunk 会造成边界表示漂移；下游增强/分离模型要单独验证边界影响。 |
