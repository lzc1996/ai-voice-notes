# Omni vs ASR TTS 专用模型选型

## 1. 内容定位

这篇解决一个架构问题：已经有 `Qwen3-Omni` / [[方向/AI语音/模型/Qwen3.5-Omni|Qwen3.5-Omni]] 这种全模态模型时，为什么还需要 `Qwen3-ASR`、`Qwen3-TTS` 这种专用语音模型。

## 2. 核心判断

- **Omni 是助手底座**：适合把文本、图像、视频、音频放在同一个上下文里理解，并直接做语音对话。
- **ASR/TTS 是工程组件**：适合明确输入输出、可缓存、可替换、可评估、可单独扩缩容的生产链路。
- **两者不是替代关系**：语音 Agent 可以用 Omni 做“大脑”，用 ASR/TTS 做“耳朵和嘴”；复杂多模态问题才让 Omni 直接处理原始音视频。

## 3. 什么时候用 Omni

- 输入不止语音，还包含图片、视频、屏幕、文档或环境上下文。
- 任务需要语音内容和视觉内容一起推理，例如视侦、视频问答、教学视频理解。
- 转写本身不是最终产物，用户要的是理解、问答、总结或行动。
- 需要 prompt context 解释领域术语、人物关系、场景背景。
- 可以接受云端/大模型成本和更复杂的延迟控制。

## 4. 什么时候用专用 ASR/TTS

- 需要产出可复查的字幕、转写文本、时间戳或对齐结果。
- 需要批处理大量音频/视频，转写结果要缓存和索引。
- 需要低延迟、稳定吞吐、独立扩缩容。
- 需要私有化、本地化或明确成本控制。
- 需要把 ASR、LLM、TTS 各层独立替换和评测。

## 5. 典型架构

### 5.1. 语音 Agent

`ASR -> LLM/Agent -> TTS`

- 默认：`Qwen3-ASR` + `Qwen3/Qwen3.5/其他 LLM` + `Qwen3-TTS`。
- 需要多模态理解时：把用户音频、画面或视频片段送入 `Qwen-Omni`。
- 好处：链路清楚，延迟和成本可控，每一层都能替换。

### 5.2. 视频理解

`ASR 生成字幕 -> VLM/LLM 检索和推理`

- 默认：先用专用 ASR 产出字幕和时间戳。
- 只有当问题依赖声音事件、画面和语音共同推理时，才把原始音视频送入 Omni。

### 5.3. 会议转写

`VAD/diarization -> ASR -> 标点/分段 -> 摘要/行动项`

- 默认不使用 Omni 直接做完整会议系统。
- 会议核心难点是说话人、段落、术语、纠错和摘要，不是单次 ASR。

## 6. 选型矩阵

| 需求 | 选 Omni | 选专用 ASR/TTS |
|---|---|---|
| 多模态推理 | 是 | 否，除非先做预处理 |
| 稳定字幕/转写 | 可辅助 | 是 |
| 时间戳/强制对齐 | 不优先 | 是 |
| 说话人分离 | 不优先 | 仍需 ASR 工程链路 |
| 本地部署 | 成本高 | 更可控 |
| 大批量处理 | 不优先 | 是 |
| 术语上下文理解 | 强 | 需 prompt/热词/后处理 |
| 端到端语音助手 | 强 | 可组合实现 |

## 7. 工程结论

- 先拆链路：ASR、LLM、TTS 三层可测以后，再决定是否把某些场景合并到 Omni。
- 不要为了“端到端”牺牲可观测性：生产系统最需要知道错在听、想还是说。
- Omni 适合高价值复杂请求；专用模型适合高频稳定流水线。
