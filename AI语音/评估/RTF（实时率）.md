# RTF（实时率）

## 0. 背景

- **出现前的问题**：传统阵列增强是帧级 DSP（谱减、维纳、MVDR），单帧成本固定，用"算法延迟 + 帧预算"就能说明实时性。深度模型上线后，单次推理成本从几十微秒涨到几毫秒甚至上百毫秒，且随模型宽度、特征分辨率、采样步数剧烈变化，帧预算这种绝对量失去可比性。
- **替代方案的缺口**：只报参数量不行（参数量与耗时不同比例，注意力对序列长度敏感）；只报算法延迟不行（那只算 buffering，不含算力）；只报 FLOPs 也不行（硬件利用率差几倍）。需要一个"与音频长度相除"的相对量，把不同长度、不同模型放进同一列。
- **出现后的谱系**：RTF 借自 ASR / TTS 评测（Kaldi 时代用于比较解码器速度），2019 年前后被 DNS Challenge、URGENT 一类挑战赛带进增强评测，成为"质量表附一列效率"的默认做法。生成式兴起后，成本结构从"一次前向"变成"NFE × 一次前向"，RTF 单值不足以描述链路，于是分化出 [[NFE（函数评估次数）]]、首包延迟、chunk 大小等并列指标；RTF 保留的角色是**唯一能和质量指标放进同一张表的成本列**。

## 1. 身份

$$\mathrm{RTF}=\frac{\text{处理该段音频所花时间}}{\text{该段音频的时长}}$$

- RTF = 0.23：1 秒音频用 0.23 秒算完，吞吐约 4.3 倍实时。
- RTF = 1：恰好实时；> 1：慢于实时，只能离线处理。
- 边界：**RTF 是吞吐指标，不是延迟指标**。RTF < 1 只说明"算得比播得快"，与"能不能实时通话"是两件事（见 §4）。

## 2. 口径四要素

报一个 RTF 必须同时给出下面四项，缺任一项就不可跨论文比较：

| 要素 | 常见分歧 |
|---|---|
| 分母（音频时长） | 纯语音时长 vs 含静音；整段 vs 按 chunk 累计 |
| 分子（计时范围） | 只算模型前向 vs 含 STFT/iSTFT、codec 编解码、vocoder、I/O |
| 硬件与精度 | A100 / V100 / RTX / CPU；fp32 / fp16；是否用 TensorRT 等编译 |
| 批与段长 | batch=1 vs 批量；整段 vs 固定 chunk；是否含 warmup |

同一模型在同一硬件上，只因"含不含编解码"和"整段还是分块"，RTF 就能差 1.5–2 倍——这已经大于很多论文宣称的"快一倍"。

## 3. 读法

| RTF 区间 | 含义 | 典型用途 |
|---|---|---|
| > 1 | 慢于实时 | 只有离线修复、批处理 |
| 0.5–1 | 接近实时，余量很小 | 单路 GPU 通话，需专用卡 |
| 0.1–0.5 | 单路实时宽裕 | 可多路并发 / 单卡多实例 |
| < 0.1 | 端侧可行区间 | 手机、耳机、助听器（还要看内存与功耗） |

链路真实延迟大致为：

```text
端到端延迟 ≈ 算法延迟（窗长 + lookahead + chunk 累积）
            + RTF × chunk 时长
            + 后处理（iSTFT / vocoder / overlap-add）
```

对**整段离线**模型，等效延迟至少是整段音频长度——所以"RTF 0.05 的整段模型"仍不能用于通话。

## 4. 常见误判

- **RTF 小 = 低延迟**：错的。整段批处理 RTF 可以很低，但必须等整句录完才出结果。实时性要看首包延迟与 chunk 策略。
- **RTF 可跨论文直接横比**：错的。硬件、含项、段长任一不同就失真；两倍以内的差距通常不足以支撑"更快"的结论。
- **RTF 与 NFE 成正比**：错。50 NFE 的小模型可能快过 5 NFE 的大模型（[[NFE（函数评估次数）|NFE]] 只数前向次数，不管每次多贵）。
- **RTF 与参数量成正比**：错。长序列注意力、特征分辨率、卷积通道数的影响常大于参数量本身。
- **RTF 与训练数据有关**：一般无关。同一架构换训练集，RTF 基本不变（[[方向/AI语音/模型/DiT-Flow|DiT-Flow]] Table VI 里两种训练集都是 0.230，就是这个道理）。
- **只看 RTF 选型**：错。压到 1 NFE 能换来极低 RTF，但 [[OVRL_MOS|OVRL]] / SIG 会掉；质量与成本要成对报。
